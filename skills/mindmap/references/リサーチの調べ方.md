# リサーチの調べ方

検討事項を決める材料を、サブエージェントに調べさせるときの調べ方。
調べる内容に合う節を選び、`## 共通` と選んだ節の本文を、調べる題材・観点・除外の一覧と一緒にサブエージェントへ渡す。
サブエージェントは会話の内容を知らないので、題材と観点は渡す文に全て書く。

## 使い分け

| 調べたいこと | 使う節 | 体数 |
| --- | --- | --- |
| 世の中の規約・標準・公式のドキュメント・考え方 | `## 公式の資料` | 題材を互いに重ならない観点に割った数 |
| 創作・芸・演出・運用の現場など、公式の資料より実践者の言葉に知恵がある題材 | `## 実践者の知見` | 出所の種類ごとに 1 体 |
| ライブラリ・API・手法の採用 | `## 技術の選定` | 候補の洗い出しに 1 体、候補ごとに 1 体 |

## 共通

### 調べ方

- 一次情報（公式のドキュメント・リポジトリ本体・標準化団体・実践者本人の言葉）を優先する
- 見つけたページは本文を読み、要約で済ませない。使う API やルールは、ソースや仕様の本文まで読む
- 公式のドキュメントに `llms.txt` があれば先に読む
- 取得できないページは、原稿（リポジトリの raw・ドキュメントのリポジトリ）・別の転載元・キャッシュ・JSON の API を探して読む
- 数値と真偽は、ページの読み取りではなく API の JSON から取る
- 取れなかった値は推測で埋めず、取れなかったことと試した手段を書く
- 版・価格・閾値・モデル名など、時期で古くなる値は、確かめた日と出典を添える
- ファイルへ書き込まない

### 返す内容

観点ごとに次を返す。

| 項目 | 内容 |
| --- | --- |
| 観点 | 調べた観点 |
| 結論 | その観点で分かったこと。1〜3 行 |
| 確度 | `高`・`中`・`低` のどれか（下の表） |
| 出典 | URL と、話し手が誰か（公式 / 実践者本人 / 第三者のまとめ / 匿名）。API の JSON は叩いた URL |
| 未確認 | 確かめられなかったことと、その理由。無ければ無し |

| 確度 | 条件 |
| --- | --- |
| 高 | 一次情報があり、別の出所でも同じことが言われている |
| 中 | 一次情報だけ、または別々の出所の第三者が同じことを言っている |
| 低 | 匿名の書き込み・出所が 1 つの第三者のまとめだけ |

出典どうしが食い違う所は、両方を並べて返す。
確度が低くても、具体的で役に立つものは捨てずに残す。

## 公式の資料

題材について、世の中の規約・標準・公式のドキュメント・考え方を調べる。

1. 題材を、互いに重ならない観点に割る。渡された除外の一覧にある内容は調べない
2. 観点ごとに、公式のドキュメント・標準・リポジトリ本体を探して読む
3. 要素ごとに、使いどころと、効かない場面を書く
4. 次に当たる要素は、結論に入れず「当てはまらない」として理由を添える
   - 特定の技術・ツールが前提で、渡された題材の技術と違うもの
   - 言語・文化に固有のもの
   - 想定する用途が違うもの
   - 渡された除外の一覧にある内容と矛盾するもの

## 実践者の知見

創作・芸・演出・運用の現場など、公式の資料より実践者の言葉に知恵がある題材について、実践者が使っている具体的な技法を集める。

渡された出所の種類ごとに集める。

| 出所の種類 | 例 |
| --- | --- |
| 実践者本人の言葉 | 本人のブログ・note・SNS の長文・インタビュー記事・対談 |
| 実践者の講座・書籍 | 養成所やワークショップの内容の紹介、書籍の要約・書評・目次、講義の書き起こし |
| 動画・音声の書き起こし | 動画・ポッドキャストで実践者が手の内を語る回 |
| 受け手と愛好者の分析 | 分析ブログ、掲示板・Q&A の議論 |
| 研究 | 論文で、技法を分類・検証したもの |

- 日本語と英語の両方で検索する。題材が日本の芸なら日本語を厚くする
- 一般論ではなく、手順・型・言い回し・実例（どの作品のどの場面か）まで書かれたページを選ぶ
- 1 つの技法について、別の出所で同じことを言っている所を探す
- 技法ごとに、名前（業界の呼び名があればそれ）・何をするか・使いどころと効かない場面・実例を返す。出典と確度は `## 共通` の形に従う。確度は、実践者本人の言葉があり別の出所でも同じことが言われていれば `高` にする

## 技術の選定

ライブラリ・API・手法の候補を集め、観点ごとに調べて比べる。
候補の洗い出しと候補ごとの調査は、別のサブエージェントに任せる。

### 条件の整理

調べたい対象から、処理の目的・言語と実行環境・既存の依存を決める。
既存の依存は、作業フォルダの依存の定義（`pyproject.toml`・`package.json` など）を読んで取る。

### 必要性の確認

標準ライブラリ・既存の依存・数十行の自作で済むかを確かめる。
済むなら、その手段と理由を返して終える。

### 候補の洗い出し

処理の目的・言語と実行環境・既存の依存を受け、候補を 3〜5 件探す。

- 今日の年を確かめ、検索語に入れる年はその値と前年にする
- 次の切り口で検索する: `{処理の目的} {言語} library {年}` / `{処理の目的} {言語} comparison` / 既存の依存のエコシステムでの定番 / 公式が推す手段
- 候補ごとに、レジストリ上の名前（`pypi/ruamel.yaml` のような `{system}/{name}`）と、リポジトリの URL を控える。名前がレジストリに実在することは `https://api.deps.dev/v3/systems/{system}/packages/{name}` で確かめる。リポジトリの URL は、版の `relatedProjects` から取る
- 目的に合わないもの・既存の依存と組み合わせられないものを落とす。Stars・最終 push などの絶対の閾値では落とさない
- 候補ごとに、名前・レジストリ上の名前・リポジトリの URL（空なら理由）・挙げた理由と出典を返す

### 候補ごとの調査

候補 1 件を、次の観点で調べる。

| 観点 | 確かめること |
| --- | --- |
| 機能適合 | 処理の目的に要る機能を持つか。足りない機能は何か |
| API の使いやすさ | 最小の使い方の短さ・型の付き方・エラーの返し方 |
| 必要性 | 標準ライブラリや既存の依存で済まないか |
| 真正性 | レジストリの `relatedProjects` のリポジトリと、渡されたリポジトリの URL が一致するか。名前の似た別物でないか。`relationProvenance` が `UNVERIFIED_METADATA`（レジストリの自己申告）なら、リポジトリ側からもそのパッケージ名を指しているか |
| 保守 | 最終 push・直近の版の出た時期・アーカイブ済みか・Issue への応答 |
| セキュリティ | 版の勧告（`advisoryKeys`）と深刻度・Scorecard |
| 依存の重さ | 依存グラフの件数と、既存の依存との重なり・衝突 |
| 採用 | Stars・依存しているパッケージの多さ・公式の推奨の有無 |
| ライセンス | SPDX の識別子と、既存の依存と組み合わせて使えるか |
| 既存との整合 | 作業フォルダの依存の定義・規約と食い違わないか |

| 取るもの | 取得先 |
| --- | --- |
| 既定の版 | `https://api.deps.dev/v3/systems/{system}/packages/{name}` の `versions[].isDefault` |
| 版のライセンス・勧告・リンク先のリポジトリ | `https://api.deps.dev/v3/systems/{system}/packages/{name}/versions/{version}` の `licenses` / `advisoryKeys` / `relatedProjects` |
| 依存グラフ | 同じ版の `:dependencies`（`.../versions/{version}:dependencies`）の `nodes` / `edges` |
| Stars・Scorecard | `https://api.deps.dev/v3/projects/{projectKey}`（`projectKey` は `github.com%2F{owner}%2F{repo}`）の `starsCount` / `scorecard.overallScore` |
| 勧告の中身 | `https://api.deps.dev/v3/advisories/{advisoryKey}` の `title` / `cvss3Score` |

`{name}` と `{version}` は URL エンコードして渡す。

返す内容は、観点ごとの所見（出典つき）・採否（勧める / 勧めない / 条件付き）と理由・処理の目的を満たす最小のコード例（import を含む）・未確認の観点と理由。

### 比較と判断

調査の結果を、観点を行・候補を列にした比較表にまとめ、推奨する候補とその理由を書く。
候補どうしの比較で決め、Stars などの絶対の閾値では落とさない。
出典が付いていない所見と、真正性を確かめられなかった候補は、表の中でそう分かるように書く。
